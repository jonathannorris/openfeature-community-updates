# OpenFeature Community Update: Sep 3 to Sep 17, 2026

_A biweekly digest of the most notable pull requests, issues, and discussions across the [open-feature](https://github.com/open-feature) org._

## TL;DR

- **Provider typing rules are under review:** [spec#430](https://github.com/open-feature/spec/issues/430) and [spec#433](https://github.com/open-feature/spec/issues/433) examine numeric coercion, accessor fit, and what determines a flag value's type.
- **OFREP metadata propagation has a proposed contract:** [protocol#85](https://github.com/open-feature/protocol/issues/85) covers preserving per-flag metadata through cached 304 and replacement 200 responses.
- **flagd readiness and sync visibility are getting stronger:** [flagd#2050](https://github.com/open-feature/flagd/pull/2050) waits for applied flag state before reporting ready, while [flagd#2051](https://github.com/open-feature/flagd/pull/2051) adds client-side freshness and reconnect metrics.
- **The Dart server SDK is advancing its v0.9 track:** [dart-sdk#170](https://github.com/open-feature/dart-sdk/pull/170) landed immutable evaluation-context snapshots, with explicit defaults, optional provider capabilities, and hook contracts in flight.
- **The ecosystem keeps expanding across runtimes and services:** [js-sdk#1455](https://github.com/open-feature/js-sdk/pull/1455) proposes an official Svelte binding, while [openfeature.dev#1485](https://github.com/open-feature/openfeature.dev/pull/1485) adds Flaghoist as an OFREP API.

## Spec & Protocol
### Proposals to watch

- **Numeric accessor behavior needs a normative rule:** [spec#430](https://github.com/open-feature/spec/issues/430) asks what providers should do when a value does not fit the requested integer or floating-point accessor. The discussion compares lossless coercion in flagd with the stricter capability model used by the provider conformance work.
- **The source of a flag value's type is still unspecified:** [spec#433](https://github.com/open-feature/spec/issues/433) highlights ambiguity for untyped backends that store values as strings, including when `TYPE_MISMATCH` should apply.
- **OFREP metadata should survive caching:** [protocol#85](https://github.com/open-feature/protocol/issues/85) proposes preserving valid per-flag keys, values, and primitive types in resolution metadata, retaining them on 304 responses and replacing or clearing them on 200 responses.

## flagd & Operator
### flagd

- **Readiness now tracks applied state:** [flagd#2050](https://github.com/open-feature/flagd/pull/2050) keeps `/readyz` unavailable until every configured sync source has updated the evaluator, addressing the gap described in [flagd#2047](https://github.com/open-feature/flagd/issues/2047) where a ready response could precede an evaluable flag set.
- **Sync freshness is becoming observable:** [flagd#2051](https://github.com/open-feature/flagd/pull/2051) adds metrics for applied configurations and their timestamps, plus gRPC stream and reconnect metrics. New client attributes are emitted alongside the legacy keys so existing dashboards can migrate.

## SDKs & Providers

- **Dart's v0.9 server implementation is becoming more explicit and safer:** [dart-sdk#170](https://github.com/open-feature/dart-sdk/pull/170) snapshots evaluation contexts immutably and preserves nested merges. [dart-sdk#176](https://github.com/open-feature/dart-sdk/pull/176) keeps legacy behavior as an opt-in boundary, [dart-sdk#177](https://github.com/open-feature/dart-sdk/pull/177) preserves rule operands, and [dart-sdk#169](https://github.com/open-feature/dart-sdk/pull/169), [dart-sdk#171](https://github.com/open-feature/dart-sdk/pull/171), and [dart-sdk#172](https://github.com/open-feature/dart-sdk/pull/172) add explicit defaults, optional provider capabilities, and requirement-indexed hook behavior.
- **Go MultiProvider handling is closing correctness gaps:** [go-sdk#580](https://github.com/open-feature/go-sdk/pull/580) preserves the full provider-state precedence order, while [go-sdk#579](https://github.com/open-feature/go-sdk/pull/579) prevents comparison evaluations from leaking goroutines. Follow-up fixes in [go-sdk#593](https://github.com/open-feature/go-sdk/pull/593) and [go-sdk#594](https://github.com/open-feature/go-sdk/pull/594) address error reasons and concurrent in-memory tracking.
- **PHP is adding the missing provider lifecycle surface:** [php-sdk#180](https://github.com/open-feature/php-sdk/pull/180) exposes evaluation and resolution metadata, and [php-sdk#187](https://github.com/open-feature/php-sdk/pull/187) adds opt-in initialization, shutdown, state tracking, provider-owned events, and recovery behavior.
- **The JavaScript SDK is broadening its UI and error-handling coverage:** [js-sdk#1455](https://github.com/open-feature/js-sdk/pull/1455) proposes an official Svelte SDK with reactive evaluations and provider status helpers, while [js-sdk#1465](https://github.com/open-feature/js-sdk/pull/1465) preserves common OpenFeature error codes through MultiProvider aggregation. The heavily discussed [js-sdk#998](https://github.com/open-feature/js-sdk/issues/998) continues to track a dedicated logging hook.
- **Swift is separating the core SDK from its logging dependency:** [swift-sdk#131](https://github.com/open-feature/swift-sdk/pull/131) introduces an `OpenFeatureLogger` protocol and makes the SwiftLog integration optional, reducing the default dependency surface.
- **.NET provider lifecycle work is addressing DI edge cases:** [dotnet-sdk#818](https://github.com/open-feature/dotnet-sdk/pull/818) fixes missed ready events through the hosting package, and [dotnet-sdk#819](https://github.com/open-feature/dotnet-sdk/pull/819) passes cancellation through provider initialization.
